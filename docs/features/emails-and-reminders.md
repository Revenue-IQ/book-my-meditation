# Emails, reminders & pre-booking

Status: built in Phase 5 (emails) · Last updated: 2026-10-27

## What it does

The app now talks to people when they're not looking at it:

- **New-slots announcement** — a preceptor plans the week, then hits **Publish week**: one batched email per eligible abhyasi listing all the newly visible slots (never one email per slot). A single slot added *after* the week was published announces itself automatically.
- **Booking confirmed** — the abhyasi gets a receipt whenever a sitting is booked (by them, or pre-booked for them); the preceptor is notified of bookings they didn't make themselves.
- **Booking cancelled** — whichever party didn't do the cancelling is told; deleting a slot emails every abhyasi whose booking died with it.
- **Reminder** — at the preceptor's lead time (default 8h, the same setting that gates the in-app "I'm coming" button), the abhyasi gets a reminder with two **one-click buttons that work without logging in**: *I'm coming* and *Cancel my booking*.
- **Pre-booking** — a preceptor can book their own slot directly for chosen regulars; those people get the normal booking email and can cancel like any other booking.
- **Settings** — a preceptor controls which types are *sent* for their sittings (4 toggles + the reminder lead time, in My Abhyasis → Settings); every user controls which types they *receive* (4 toggles — abhyasis under "Email preferences" on the Sittings page, preceptors inside the same Settings panel). All default ON; there is no master switch.

## How it works

- **Send gate** (spec rule): an email goes out only if the slot's preceptor has that type enabled for **sending** AND the recipient has it enabled for **receiving**. One house rule on top: the person who performed an action isn't emailed about their own action — except the abhyasi's booking confirmation, which is their receipt and always applies.
- **Schema** (migration `0005_emails_reminders`): `email_pref` table (per-user receive toggles; a missing row = all ON, rows appear on first edit); send toggles + `home_timezone` on `preceptor_pref`; `announced_at` on `slots`; `reminder_sent_at` + unique `action_token` (UUID, `gen_random_uuid()`) on `bookings`.
- **Transport** ([api/src/mailer.ts](../../api/src/mailer.ts)): Resend's REST API via plain `fetch` (no SDK dependency). Three modes by env: no `RESEND_API_KEY` → emails print to the server log (local dev stays keyless); key + `EMAIL_REDIRECT_TO` → everything delivers to that one inbox with the real recipient in the subject (the pre-domain cloud mode — Resend without a verified domain only delivers to the account owner anyway); key alone + `EMAIL_FROM` → normal delivery once the domain is verified. Switching modes is env-only, no code changes.
- **Wording** ([api/src/lib/emails.ts](../../api/src/lib/emails.ts), pure/testable): every sitting time is written in the preceptor's **home timezone** with the zone label printed ("Tue, Nov 3, 7:00 AM GMT+5:30"); the reminder leads with relative time ("in about 8 hours"). Orchestration (who gets what) is [api/src/notify.ts](../../api/src/notify.ts); all sends are fire-and-forget so an email failure never fails or slows the API response.
- **Publish week**: `POST /api/preceptor/publish-week` announces every future, not-yet-announced slot in the visible week; `announced_at` is set *before* sending (only unmarked rows), so a double click can never double-send. The week-page button shows the unannounced count; unannounced slots carry a violet dot. Auto-announce on create decides "was this week published?" by looking for any announced slot in the same Monday-start week *in the preceptor's home timezone* (the server can't know the browser's week).
- **Reminders**: a sweep runs at boot (catching up after downtime) and every minute; due = active booking, no reminder yet, active preceptor, slot starts within the lead time but hasn't started. Each booking is *claimed* (`reminder_sent_at` set) before sending so concurrent sweeps can't double-send; a booking whose email is gated off is still claimed and never reconsidered.
- **One-click actions**: `GET /api/booking-action/:token/confirm|cancel` — the only auth-free API route; the unguessable 122-bit token in the URL is the whole authorization. Replies with a small branded HTML page; handles already-cancelled, already-started and dead links gracefully. A one-click cancel triggers the normal cancellation email to the preceptor.
- **Pre-booking**: `POST /api/preceptor/slots/:id/prebook` runs each person through the full `bookSlot` guards (capacity row-lock, link, visibility, duplicates); per-person failures are reported back, not fatal. UI lives in the slot detail popup; restricted slots only offer the people who can see them.

## Decisions

- **Resend without a domain, by design** — the domain purchase is pending on someone else, so the phase was built against Resend's test mode: `onboarding@resend.dev` sender + redirect-all-to-owner inbox, switchable to the real domain purely by env. Rejected: Gmail SMTP as a stopgap (throwaway code, ~500/day cap, poor deliverability); waiting for the domain (blocks the whole phase for no reason).
- **Emails worded in the preceptor's home timezone; the app stays browser-local** — a preceptor's circle generally lives in one timezone, and someone travelling can convert *from* their home zone more easily than from a stranger's. Emails are frozen text and can't adapt to the reader, so they carry the home zone with an explicit label; the web app keeps adapting to the browser, with a "times are shown in your local timezone" note. Rejected: per-user stored timezones (capture machinery for a rare case — can be added later without undoing anything); pinning the whole app to the home timezone (inconvenient for everyone actually living elsewhere); hardcoding IST (wrong the moment one preceptor is abroad).
- **Home timezone is a required admin input, not a browser auto-capture** — set on the create-preceptor form (pre-filled with the admin's detected zone), editable in the admin's edit modal. An explicit value can't be corrupted by a preceptor opening the app while travelling. There is deliberately **no silent fallback to a guessed zone**: the column defaults to Asia/Kolkata only as a backfill for pre-Phase-5 rows. Changing it never moves existing slots (they're UTC instants) — only how times are worded, and the UI says so.
- **`email_pref` is one table for every role, not the planned `abhyasi_pref`** — preceptors receive emails too (booking notifications, plus everything as abhyasis of their own preceptors), so receive toggles are recipient configuration, not an abhyasi feature. The Phase-1 schema decision to defer this table still held; only its name/scope changed at build time.
- **A missing `email_pref` row means "all ON"** — the spec defaults everything to ON, so rows exist only for people who changed something. No backfill, no lazy-create on read.
- **"Published week" is tracked per slot (`announced_at`), not per week** — no weeks table exists; a timestamp on the slot gives idempotent publishing, the "N new" button count, and the auto-announce check for free, and naturally handles slots added across week boundaries.
- **Reminders also go to already-confirmed bookings** — the reminder is still useful as a reminder; its confirm button is idempotent. Rejected: skipping confirmed bookings (someone who confirmed five days early still wants to be reminded).
- **A booking made inside the reminder window gets a reminder too** (on the next sweep, right after its confirmation email). Slightly chatty, but the reminder carries the one-click links the confirmation doesn't; suppressing it would need a "booked recently" rule with its own edge cases.
- **Claim-then-send for reminders** — `reminder_sent_at` is set before the send; a crash between claim and send loses one reminder rather than ever double-sending. The better failure mode for email.
- **One-click links use a stored random token, not a signed URL** — no signing secret to manage or rotate; the token is born with the booking (`gen_random_uuid()` column default) and dies with it. GET with side effects is accepted deliberately: email clients only follow clicks, and the actions are idempotent per status checks.
- **Copy-last-week now uses the home timezone** for its +7-days calendar math ([api/src/lib/tz.ts](../../api/src/lib/tz.ts), unit-tested across both DST directions) — closing the Phase-2 caveat that it used the server's own timezone, which on cloud is UTC.
- **Timezone picker is a curated ~35-zone list, not the full IANA set** — `Intl.supportedValuesOf('timeZone')` has ~420 entries, unusable in a plain select (first attempt; revised on user feedback). The curated list (`COMMON_TIMEZONES` in `web/src/api.ts`) holds one familiar city per plausible region, sorted west→east, each labeled with its offset computed live ("Asia/Kolkata (GMT+5:30)") so DST zones always read correctly. The detected and currently-stored zones are always merged in, so no valid value can be dropped — this also absorbs Chrome's legacy `Asia/Calcutta` alias, which earlier made the edit modal silently show the list's first entry (a real bug caught in testing). A genuinely missing zone is a one-line addition to the list.

## Future

- Verify the domain with Resend, set `EMAIL_FROM`, remove `EMAIL_REDIRECT_TO` — then do a deliverability pass (SPF/DKIM live checks). No code changes expected.
- Per-abhyasi timezone wording in emails, if cross-timezone pairs ever become common — additive change in `notify.ts` (pick a different zone per recipient).
- Phase 6 reworks deployment; the reminder sweep's in-process `setInterval` assumes a single always-on API container (true today) — revisit if that changes.
